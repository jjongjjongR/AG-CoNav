## 0. 목적을 정확히 잡는다

실제 OS1-32 에서 azimuth window 를 좁히는 것은 **가능하다.** 제조사 문서로 확인한
내용(2026-08-13):

| | |
|---|---|
| 설정 | `set_config_param azimuth_window [최소, 최대]` — 단위 **밀리도** |
| 지원 | **Gen1 OS1 전 리비전**, Gen2 OS01, Gen2 OS2. 펌웨어 **v2.0.0 이후 계속** (v2.5.3 / v3.0 / v3.1 매뉴얼에도 있음) |
| 효과 | 창 안의 데이터만 반환. **패킷율·데이터율이 실제로 내려간다.** 소비전력·발열도 감소 |

**하드웨어 개조가 아니라 정식 설정값이다.** 채널 32개, 수직 FOV ±21.2°, 회전
주기, 각해상도가 전부 그대로이므로 **여전히 OS1-32 다.**

출처:
- <https://static.ouster.dev/sensor-docs/image_route1/image_route2/sensor_operations/sensor-operations.html>
- <https://static.ouster.dev/sensor-docs/image_route1/image_route2/common_sections/API/sensor_configuration_description.html>
- <https://data.ouster.io/downloads/software-user-manual/firmware-user-manual-v2.5.3.pdf>

실기와 시뮬의 차이 하나: 실제 센서는 프레임 폭(`columns_per_frame`)을 유지한 채
창 밖 컬럼을 무효로 표시하고(`column_window` 메타데이터), Gazebo 쪽은 아예 좁은
폭의 점군을 낸다. **유효 점 자체는 같아 매핑 결과에는 차이가 없다.**

**그러나 360°의 1024개 점을 80° 안으로 몰아넣는 기능은 아니다.**

| | |
|---|---|
| ❌ 목적이 아닌 것 | λ 를 공짜로 몇 배 늘리기 |
| ✅ 목적 | 쓸모없는 방향의 데이터를 버리면서 mapping 품질을 유지할 수 있는가 |

즉 이 실험은 **정확도 향상법이 아니라 데이터 처리 효율 개선법**을 검증한다.

> 이전 대화에서 "시야를 좁히면 같은 샘플로 밀도 6배"라고 적은 적이 있는데,
> 그건 **각해상도를 4.5배 올린 다른 센서**를 만드는 것이지 azimuth window 가
> 아니다. 정정한다.

### 근거

실측: **지면 반사의 96.9% 가 h ∈ [0°, 60°] 에 집중**되어 있는데 설정은 ±180°
전체를 쏜다. 스캔당 32,768 빔 중 **반사가 오는 것은 7~15%** 뿐이다.

## 1. 설계

### 1-1. 먼저 10초짜리 확인 — 좌표 규약부터

**전체 비행부터 하면 안 된다.** 정지 상태에서 PointCloud 한 scan 을 뽑아
방위각 분포를 직접 센다.

```
전체 ground point 수
  0° ~  60° 안의 점 수
-10° ~  70°
-15° ~  75°
-30° ~  90°
```

**`-10° ~ 70°` 가 ground return 의 ≥95% 를 보존하는지** 확인한 뒤에 진행한다.
기존 분석(h=atan2(y,x), 센서 프레임)이 맞을 가능성이 높지만 실제 좌표 규약을
실험 전에 못박아야 한다.

### 1-2. 실험군 — **측정 후 대칭 창으로 바꿨다**

사전 확인(§4-1)을 돌린 결과 반사는 **0° 를 중심으로 대칭**이었다. 원안의
비대칭 창(−10°~70° 등)은 한쪽만 잘라내는 잘못된 설계였다.

| | window | 폭 | ground 유지율(실측) |
|---|---|---|---|
| A0 | 전체 | 360° | 100% |
| A1 | **−60° ~ +60°** | **120°** | **98.68%** |
| A2 | −45° ~ +45° | 90° | 93.98% |
| A3 | −40° ~ +40° | 80° | 88.94% |
| A4 | −30° ~ +30° | 60° | 73.56% |
| A5 | −20° ~ +20° | 40° | 53.89% |

**120° 가 가장 현실적인 후보다.** 발사 광선을 1/3 로 줄이면서 지면 반사는
1.3% 만 잃는다.

### 1-3. 소프트웨어 마스킹부터 — 7번 실험과 같은 bag 재사용

각 점의 방위각을 `θ = atan2(y, x)`(센서 프레임)로 계산해 window 밖을 버린다.
한 번의 비행 데이터로 5개 조건을 전부 비교할 수 있다.

이 단계에서는 **지도 품질 효과만** 본다.

### 1-4. 고정 조건

7번 실험과 동일. **월드 `Seongdong_gu_100x100_dynamic`**(100 x 100 m 테스트 월드),
고도 84 m / 속도 10 m/s / 간격 10 m / OS1-32 1024×10 / 셀 0.10 m.
소프트웨어 마스킹은 7번 실험과 **같은 raw bag(`bags/RAW_v10`)** 을 재생한다.

> 본 맵에서는 못 한다 — 정답 heightmap 이 테스트 월드에만 있어 FN/FP 를 잴 수
> 없다. **권장값은 이 월드·고도 84 m·간격 10 m 조건에서만 검증된 것이다.**

## 2. 기록할 값

7번 실험과 거의 같되 **두 가지를 반드시 나눠 기록한다**:

| 지표 | |
|---|---|
| 전체 point 유지율 | 처리량 절감 |
| **ground point 유지율** | **품질 유지 여부** |

**이 실험의 핵심은 "전체 데이터는 많이 버렸는데 ground data 는 거의 안 버렸는가"** 다.

나머지: λ / 커버리지 / 높이 RMS / 단차 중앙 / wheel FN / leg FN / FP / 매퍼 처리 시간

### 성공 형태의 예

```
360°   전체 point 100%   ground point 100%   wheel FN 10.66%
 80°   전체 point  25%   ground point  97%   wheel FN 10.8%
```

이러면 **지도 품질은 그대로인데 처리 데이터가 1/4** 이다. 결론은
"azimuth 제한은 정확도 향상법이 아니라 데이터 처리 효율 개선법"이 된다.

## 3. Gazebo SDF 검증 — 각해상도를 반드시 유지할 것

소프트웨어 마스킹으로 최적 window 를 찾은 뒤 **그 조건 하나만** SDF 에 적용한다.

Gazebo 에서 `<samples>` 는 sweep 당 생성하는 ray 수, `<min_angle>/<max_angle>` 은
ray 가 생성되는 각 범위다.

### 하면 안 되는 설정

```xml
<samples>1024</samples>
<min_angle>-0.174533</min_angle>   <!-- -10° -->
<max_angle>1.221730</max_angle>    <!--  70° -->
```

80° 안에 1024 ray 를 넣으면 **각해상도가 약 4.5배 증가**한다. 이건 OS1 의
azimuth window 가 아니라 **다른 고해상도 가상 LiDAR** 다.

### 올바른 설정 — 1024/360° 의 각해상도 유지

| FOV | 대응 samples |
|---|---|
| 360° | 1024 |
| **120°** | **341** |
| 90° | 256 |
| 80° | 228 |
| 60° | 171 |

```xml
<horizontal>
    <samples>341</samples>
    <resolution>1</resolution>
    <min_angle>-1.047198</min_angle>   <!-- -60° -->
    <max_angle>1.047198</max_angle>    <!-- +60° -->
</horizontal>
```

이렇게 해야 "360° OS1 에서 필요 없는 영역만 잘라낸 것"에 가까운 시뮬레이션이
된다. Ouster 의 실제 `azimuth_window` 도 특정 ROI 로 출력 범위를 제한하는
기능이고, SDK 에서 lidar mode 의 `columns_per_frame` 과 azimuth window 에 따른
`column_window` 가 별도로 표현된다.

## 4. 측정 결과

### 4-1. 방위각 분포 사전 확인

`analyze_raw_points.py bags/RAW_v10 --stride 20` — 스캔 215개, 지면 반사
713,971점(스캔당 3,321점, `r ≥ 2.5 m` 인 점만).

| 방위각 (30° 폭) | 비중 |
|---|---|
| −180 ~ −120 | 0.00% |
| −120 ~ −90 | 0.01% |
| −90 ~ −60 | 0.22% |
| **−60 ~ −30** | **12.40%** |
| **−30 ~ 0** | **37.23%** |
| **0 ~ +30** | **36.33%** |
| **+30 ~ +60** | **12.72%** |
| +60 ~ +90 | 1.05% |
| +90 ~ +180 | 0.05% |

**반사는 0° 를 중심으로 대칭이고 ±60° 안에 98.68% 가 들어 있다.**

> **이전 분석의 "96.9% 가 h ∈ [0°, 60°]" 는 틀렸다.** 실제 분포는 0° 중심
> 대칭이고, [0°, 60°] 로 자르면 절반(49.05%)을 버린다. §1-2 의 실험군을
> 대칭 창으로 다시 짠 이유다. **전체 비행 전에 10초 확인부터 하라는 설계가
> 실제로 설계 오류를 잡아냈다.**

### 4-1-1. 좌표 규약을 `ring` 필드로 확정했다

한 스캔을 ring(채널 번호)별로 갈라 보면 축의 역할이 그대로 드러난다.

```
ring 12   x 82.0..83.3   y -18.7.. 19.0   z  -7.2.. -6.9
ring 15   x 76.9..83.3   y -29.3.. 73.4   z  -1.3.. -1.0
ring 23   x 78.7..82.6   y -29.1.. 69.4   z  14.4.. 19.4
ring 31   x 77.2..81.5   y -29.2.. 69.8   z  30.4.. 41.3
```

| 축 | 정체 |
|---|---|
| **x** | **연직 하향.** 어느 ring 이든 78~83 m 로 거의 일정 = 지면까지의 높이 |
| **z** | **32개 채널(ring)이 퍼지는 방향.** ring 마다 좁은 띠, ring 12→31 에서 −7 → +41 m |
| **y** | **1024개 샘플이 훑는 방향.** 같은 ring 안에서 −29 ~ +70 m 로 넓게 퍼짐 |

즉 **`θ = atan2(y, x)` 가 1024 샘플의 sweep 각이 맞다** — 이 실험에서 좁히려는
바로 그 축이다. §4-1 의 분포는 유효하다.

기체가 +x(map) 로 기수를 두고 날므로 라이다 z 는 진행 방향, y 는 횡방향이다.
따라서

- **ring 32개 = 진행 방향 footprint.** ring 0 이 φ = −21.2°, ring 31 이 +21.2°
  로 사양(±21.2°)과 정확히 일치한다. 80 m 상공에서 ±31 m, 총 62 m
- **sweep 1024개 = 횡방향 footprint.** ±60° 면 ±138 m

**스트립 간격이 10 m 인데 횡방향으로 ±138 m 를 보고 있다.** 이 실험이 유망한
이유가 여기 있다 — 넓은 sweep 은 거의 전부 중복 관측이다.

### 4-2-1. 목적은 달성됐다 — ±60° 는 광선 1/3 에 품질 동일

| | 광선 | ground 유지 | wheel FN |
|---|---|---|---|
| 전체 360° | 1024 | 100% | 9.849 / 11.222 |
| **±60°** | **341 (1/3)** | **98.68%** | **9.780 / 11.157** |

두 차수 모두 차이가 −0.07 %p 로 **잡음 이하**다. 자기 셀 수도 같다.
§2 가 적어둔 "성공 형태" 그대로다 — **버리는 데이터는 2/3 인데 지도는 그대로.**

### 4-2-2. 그런데 더 좁히면 오히려 좋아진다 (±30° 만 빼고)

±45° 는 광선 1/4 에 wheel FN 이 **−0.66 / −0.74 %p** 로 오히려 개선되고,
±25° 는 광선 1/7 에 **−1.52 %p** 다. 두 차수가 같은 방향을 가리킨다.

**단 ±30° 와 ±35° 는 반대로 나쁘다** — ±30° 는 전체 대비 **+1.48 / +1.58 %p**,
잡음의 25배다. 두 차수 모두, 양옆(±25°, ±40°)은 멀쩡한데 그 사이만 무너진다.

### 4-2-3. **7번 실험과 같은 자리에서 무너진다**

거리 게이팅과 방위각 윈도우는 전혀 다른 필터인데, wheel FN 이 나빠지는 구간을
**횡방향 도달 거리**로 놓고 보면 정확히 겹친다.

각 조건을 **자기 차수의 전체(360°/제한없음) 대비 차이**로 놓는다.

| 횡방향 도달 | 7번 실험 (거리 게이트) | 8번 실험 (방위각) |
|---|---|---|
| 29 m | — | ±20° **−1.48** ✅ |
| 36 ~ 37 m | 87.5 m **−0.44** ✅ | ±25° **−1.52** ✅ |
| 41 m | 90 m **−0.44** ✅ | — |
| **46 m** | 92.5 m **+0.45** ❌ | ±30° **+1.58** ❌ |
| **51 m** | 95 m **+0.85** ❌ | — |
| **56 m** | 97.5 m **+0.49** ❌ | ±35° −0.02 (이득 소멸) |
| 60 m | 100 m +0.07 (중립) | — |
| 67 m | 105 m −0.11 | ±40° **−0.55** ✅ |
| 80 m 이상 | 110~120 m **−0.24 ~ −0.46** ✅ | ±45° **−0.74** ✅ / ±50° −0.33 |

**두 실험이 독립적으로 같은 자리에서 무너진다 — 횡방향 도달 46~56 m.** 양쪽
바깥(36~41 m, 67 m 이상)은 둘 다 개선된다.

다만 **크기는 일치하지 않는다.** 같은 46 m 에서 게이트는 +0.45 인데 방위각은
+1.58 이다. 위치가 겹치는 것은 확실하고, 세기까지 같은 현상이라고 말할 근거는
아직 없다.

7번 실험에서 FN 초과가 비행선 바로 아래에 몰렸던 것(1.9배)과 방향은 맞는다 —
스트립 간격 10 m 대비 도달 거리가 4.6~5.6배인 구간이다.

> **메커니즘은 여전히 확인하지 못했다.** 두 실험 다섯 차례에서 재현되고 공간
> 서명까지 일치하지만, 왜 그 띠에서 무너지는지는 설명하지 못한다.
> **실무적으로는 "횡방향 도달 46~60 m 구간을 피하라"로 충분하고, 그것이 지금
> 확실하게 말할 수 있는 전부다.**

### 4-3. Gazebo SDF 검증

#### 4-3-0. 첫 시도는 무효였다 — 편집이 시뮬레이션에 닿지 않았다

`set_lidar_azimuth.sh` 가 고친 파일은
`src/agconav_description/models/agconav_drone/model.sdf` 였는데, 속도 비행이 쓰는
`Seongdong_gu_100x100_dynamic` 월드가 스폰하는 모델은
`src/agconav_test_worlds/models/agconav_drone_dynamic/model.sdf` 다.
**이름이 달라 편집이 전혀 반영되지 않았다.**

발행되는 점군을 직접 확인해서 잡았다.

| | width | 빔 | 반사 | θ 범위 |
|---|---|---|---|---|
| 전체 | 1024 | 32,768 | 2,461 (7.5%) | −1.2 ~ +52.3° |
| ±25° (반영 안 됨) | **1024** | 32,768 | 2,265 | **+1.2 ~ +53.0°** |

수정 전 세 번의 비행은 전부 같은 센서였다는 뜻이고, 그래서 **의도치 않게
비행 간 재현성 측정이 됐다.**

| 라벨 | 실제 조건 | 공통셀 wheel FN |
|---|---|---|
| full | 전체 360° | 10.607 |
| a45 | 전체 360° | 11.347 |
| a25 | 전체 360° | 10.741 |

**서로 다른 비행끼리는 0.74 %p 안의 차이를 신뢰할 수 없다.** 재생 실험의 잡음
바닥(0.06~0.10 %p)보다 **10배 크다** — 필터 비교를 재생으로 한 것이 왜 옳았는지
보여주는 수치다.

> 같은 결함이 `set_lidar_mode.sh` 에도 있었다. **`2. 최적 라이다 센서 조합 실험.md`
> 의 측정값은 전부 무효다** — 그 문서 맨 위에 적어 두었다.

#### 4-3-1. 수정 후 재측정 (maps_test/sdf_cmp2, 공통 591,293셀)

각해상도는 1024/360° 로 유지했다(±45° → 256 샘플, ±25° → 142 샘플).

| SDF 설정 | 샘플 | 점군 | 점/스캔 | λ | 자기 셀 | RMS | **wheel FN** | leg FN |
|---|---|---|---|---|---|---|---|---|
| 전체 360° | 1024 | 3,588 | 3,398 | 12.18 | 994,716 | 0.05903 | 10.892 | 3.271 |
| **±45°** | **256** | **3,987** | 3,226 | **12.86** | 994,634 | **0.05184** | **7.249** | 2.866 |
| ±25° | 142 | 3,962 | 2,236 | 8.93 | 987,259 | 0.05184 | 9.361 | 2.820 |

**방향은 소프트웨어 마스킹과 같고, 크기는 훨씬 크다.**

##### 두 가지 이유 중 하나는 진짜고 하나는 시뮬레이터 인공물이다

**(1) 진짜 — 점군이 작아져 드롭이 줄었다.** 점군 수 3,588 → 3,987 (**+11%**).
좁은 창은 메시지가 1/4 이라 브리지·매퍼가 덜 놓친다. 그래서 점/스캔은 5% 줄었는데
**λ 는 오히려 12.18 → 12.86 으로 올랐다.** 실기에서도 대역폭·연산이 줄어드는 것은
같으므로 이 이득은 유효하다.

**(2) 인공물 — Gazebo 의 넓은 FOV 라이다가 덜 정확하다.**

| | 높이 RMS 개선 |
|---|---|
| 소프트웨어 마스킹 ±45° (같은 점군의 부분집합) | **−1.1%** (0.06398 → 0.06326) |
| SDF ±45° (좁은 창으로 직접 발사) | **−12.2%** (0.05903 → 0.05184) |

**같은 각도 영역인데 SDF 쪽 점이 훨씬 정확하다.** 즉 gpu_lidar 는 360° 를 쏠 때
90° 만 쏠 때보다 점 자체가 부정확하다(넓은 FOV 를 여러 면으로 렌더링하는 데서
오는 것으로 보인다). **실제 OS1 의 정확도는 azimuth window 폭에 좌우되지
않으므로 이 몫은 실기로 넘어가지 않는다.**

> **그래서 실기 성능 추정에 쓸 값은 소프트웨어 마스킹 쪽이다.** SDF 측정은
> "방향이 맞다 + 드롭이 준다"까지만 근거로 삼는다. −3.6 %p 를 그대로 믿으면 안
> 된다.

## 5. 결론

### 5-1. 목적은 달성됐다

> **쓸모없는 방향의 데이터를 버리면서 지도 품질을 유지할 수 있는가 — 그렇다.**

`±60°`(폭 120°, 341 샘플)에서 **광선은 1/3, 지면 반사는 98.68% 유지, wheel FN
차이는 −0.07 %p 로 잡음 이하**다. 두 차수 모두 같다. §2 가 미리 적어둔 성공
형태와 일치한다.

### 5-2. 권장값

| | 폭 | 샘플 | 근거 |
|---|---|---|---|
| **±45°** | 90° | **256** | 품질도 좋아진다. 마스킹 −0.66/−0.74 %p, SDF 도 같은 방향 |
| ±60° | 120° | 341 | 보수적 선택. 품질 변화 없음이 확실, 커버리지 손실 0 |
| ±25° | 50° | 142 | 마스킹으로는 가장 좋지만 커버리지 −0.8~1.2%, 나쁜 띠 바로 옆 |

> **`±45°` (min/max_angle ∓0.785398 rad, `<samples>256`) 를 권장한다.**
>
> - 광선 1/4, 지면 반사 94% 유지
> - wheel FN 은 나빠지지 않고 소폭 개선(마스킹 기준 −0.7 %p)
> - **커버리지 손실 사실상 0** (994,634 vs 994,716 셀)
> - 횡방향 도달 80 m — 스트립 간격 10 m 의 8배로 여유가 크다
>
> **절대 쓰면 안 되는 값: ±30°** (wheel FN +1.5 / +1.6 %p, 잡음의 25배).
> ±35° 는 나빠지지는 않지만 이득이 사라진다 — 좁힐 이유가 없어진다.

### 5-3. 이 실험이 남긴 더 큰 것

**서로 다른 두 필터가 같은 나쁜 띠를 가리켰다** (§4-2-3). 거리 게이팅과 방위각
윈도우는 자르는 방식이 전혀 다른데, **횡방향 도달 46~60 m** 에서 나란히 무너진다.
스트립 간격 10 m 대비 4.6~6배인 구간이다.

이건 필터의 성질이 아니라 **비행 격자와 관측 기하 사이의 상호작용**이라는 뜻이고,
지금까지 "λ 하나로 설명된다"고 봤던 그림에 들어맞지 않는 항이 있다는 신호다.
**메커니즘은 규명하지 못했다.**

### 5-4. 부수적으로 드러난 결함 두 개

| | |
|---|---|
| SDF 편집이 시뮬레이션에 도달하지 않음 | 스크립트가 두 모델 파일을 모두 고치도록 수정. **`2. 최적 라이다 센서 조합 실험.md` 는 이것 때문에 전체 무효** |
| 공통 격자 인덱싱의 은행가 반올림 | `eval_common_cells.py` 원점을 셀 중심으로 옮기고 위상 검사 추가 (`7번 실험` §3-2) |

둘 다 **"설정을 바꿨다고 믿었지만 실제로 바뀌었는지 확인하지 않았다"** 는 같은
종류의 실수다. 이후 실험에서는 **바꾼 설정이 실제 데이터에 나타나는지 먼저
확인한다**(점군의 `width` 와 θ 범위를 직접 본 것처럼).

### 5-5. 이 실험의 한계 — 어디까지 믿을 수 있나

| | |
|---|---|
| **조건 1개** | 고도 84 m, 간격 10 m, 속도 10 m/s, 테스트 월드 하나. 창의 가치는 결국 **횡방향 도달 거리 대 스트립 간격**의 비율에서 나오므로, **간격이나 고도가 바뀌면 ±45° 를 그대로 쓸 수 없다** |
| **SDF 수치는 과장돼 있다** | Gazebo 가 360° 라이다를 덜 정확하게 렌더링한다(§4-3-1). 실기 추정에는 **소프트웨어 마스킹 값(−0.7 %p)** 을 쓰고 SDF 의 −3.6 %p 는 쓰지 않는다 |
| **재현은 재생 안에서만** | 마스킹 잡음 바닥 0.06 %p 는 같은 bag 기준이다. **다른 비행끼리는 0.74 %p** 라 −0.7 %p 는 새로 날리면 겨우 구분되는 크기다 |
| **±30° 메커니즘 미규명** | 두 차수 모두 +1.5 %p 로 재현되고 7번 실험과 위치도 겹치지만 이유를 모른다 |
| **실기 미검증** | 실제 OS1-32 에 `azimuth_window` 를 걸어본 것이 아니라 시뮬레이션이다 |
