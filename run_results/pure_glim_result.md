## 목표

지금까지 쌓인 모든 커스텀 우회(수동 청크분할, GPS 사후결합, 메모리 가드
수정)를 걷어내고, GLIM 공식 문서가 권장하는 표준 방식 그대로 100x100 지역의
2.5D elevation map을 얻는다. 조건(5m AGL, 5m/s, 4m 간격) 유지, 재비행 없이
기존 GPS 포함 bag(`bags/velocity_4m_5mps_gps_attempt2`) 재사용. 정확도 개선용
파라미터 튜닝·GPS결합 없음. 허용 예외 2개만: ①bag 끝 자유낙하 구간(t>2129.67s)
처음부터 제외, ②지도 생성 시 격자 크기 크래시 방지 상한(max_grid_cells).

## 1. GLIM 표준 설정 재검증

패키지(`ros-jazzy-glim` 1.2.2) 미수정 원본 config와 직접 diff 대조한 결과:
- 진짜 패키지 기본값은 **GPU 조합**(`config_odometry_gpu.json` 등) — 이 VM은
  GPU가 없어(`nvidia-smi` 없음) 실행 불가.
- 기존 실험이 쓰던 `CT+passthrough+pose_graph`는 "IMU 회전이 안 잡히는
  teleport bag" 대응용 특수 조합이었다. 패키지에는 진짜 CPU 표준 조합
  (`config_odometry_cpu.json`+`config_sub_mapping_cpu.json`+
  `config_global_mapping_cpu.json`, LiDAR-IMU tight coupling)이 세트로
  이미 존재했다 — GPU 다음 우선순위 표준으로 채택해 `glim_config_cpu_std/`
  구성.
- CT 조합도 재검토: 기존 `glim_config/`의 `constant_velocity_inf_scale`이
  원본 기본값(1e3)에서 1e0으로 낮춰져 있었고 근거가 다른 실험(84m/8m/s)에서
  복사된 것이었다 — 완전 미수정 원본(1e3)만 쓰는 `glim_config_ct_std/`를
  별도 구성.

## 3. 점진적 확장

`glim_rosbag`(GLIM 공식 배치 처리 도구, ROS 파라미터 `start_offset`/
`playback_duration`/`auto_quit`/`dump_path` 사용 — 수동 청크분할이 아니라
도구 자체에 내장된 단일 실행 인터페이스)로 CT 표준을 단계적으로 확장:

| 확장 단계 | 구간 | 결과 | GT 대비 |
|---|---|---|---|
| 1 (1단계) | t=33~90s (57초, 첫 코너 전) | 크래시 없음 | 발산 자동탐지 없음(값 요동), 최종오차 79.6m |
| 2 | t=0~800s (여러 코너 포함) | 크래시/OOM 없음, RSS 최대 ~1.45GB | 발산 자동탐지 t=22.3s, 최대오차 157.0m |
| 3 (최종) | t=0~2129.67s (자유낙하 직전까지 전체) | **크래시/OOM 없음**, RSS 최대 ~4.9GB(82.7%, 저장 순간 피크) | 발산 자동탐지 t=29.7s, 최대오차 199.94m |

**"발산"을 정지조건으로 볼지에 대한 판단**: 오차가 크지만(수십~200m대)
값이 유한하고 경계가 있어(수백~수천m로 폭주하지 않음), 이 프로젝트의
이전 세션(SUMMARY.md "GLIM Phase 2 파라미터 튜닝")이 **같은
`constant_velocity_inf_scale=1e3`**(이번 실험이 "미수정 원본값"으로
다시 채택한 바로 그 값)으로 전체 bag을 이미 검증해 "치명적 발산(물리적
으로 불가능한 값)은 없고 실비행 구간 평균 ATE 68.6m, 최대 137.3m"임을
확인해뒀던 것과 같은 양상이다. 이걸 "GLIM 자체·설정·환경의 실제 정확도"
로 판단하고 지시사항의 정지조건(파국적 발산/OOM)에는 해당하지 않는다고
보아 전체 구간까지 끝까지 밀어붙였다. 세 단계 모두 크래시/OOM은
한 번도 없었으므로 **100x100 커버 가능한 전체 비행 구간(자유낙하 제외)을
전부 처리했다** — 시간/코너 수 기준의 "부분 커버리지"가 아니라, 처리
자체는 전체를 완주했다(다만 아래 4-2처럼 정확도 문제로 실제 유효
커버리지는 낮다).

## 5. 결론

### 커스텀 코드 문제였나, GLIM/설정/환경 자체의 문제였나 — 후자로 확정

1단계(정확도 튜닝·GPS결합·칼만필터·GICP 등 다운스트림 커스텀 코드를 전부
배제하고, GLIM 원시 궤적만 GT와 대조)부터 이미 GT 대비 1~2m는커녕 수십m
단위로 벗어났고(CT 표준 기준 t=98s에 79.6m), 전체 bag으로 확장해도 같은
양상(최대오차 199.94m, bounded)이 유지됐다. 커스텀 코드는 이번 실험
어디에도 관여하지 않았으므로(원시 GLIM 궤적 → 단순평균 지도만 사용),
**이 부정확성은 GLIM 자체의 궤적 추정(odometry+pose-graph) 단계에서
발생하는 것이며, 다운스트림 커스텀 코드의 문제가 아니다.**

### 근본 원인 추정 (진단, 재현만 — 이번 실험 범위에서 고치지 않음)
- 이 VM에 GPU가 없어 GLIM 패키지의 진짜 기본(가장 검증된) 조합을 못 씀 —
  CPU 대안 두 가지(LiDAR-IMU tight coupling, CT LiDAR-only) 모두 이
  시뮬레이터 데이터에서 GT 대비 심각하게 부정확했다.
- CPU-IMU 표준은 `IMU better ratio`가 반복적으로 0.5 미만(IMU 예측이
  안 쓰는 것보다 나쁨) — 이 시뮬레이터의 IMU 잡음 모델/LiDAR-IMU 외부보정
  조합이 GLIM의 LiDAR-IMU 타이트 커플링과 구조적으로 안 맞는 것으로
  추정된다.
- CT(LiDAR-only)는 IMU 문제는 피하지만, per-point 타임스탬프가 없는(의사
  시간순으로만 근사하는) 이 LiDAR 데이터 + 저고도(5m AGL) 평탄 지형에서의
  약한 기하학적 제약(수직 구조물 부족)이 결합해 등속/스무딩 사전확률만으로는
  누적 드리프트를 못 잡는 것으로 보인다.

### 100x100 커버리지
전체 비행 구간(자유낙하 제외) 처리 자체는 크래시/OOM 없이 완주했다 —
시간/코너 수 기준으로는 100%를 처리했다. 그러나 **궤적 부정확성 때문에
실제 유효 커버리지(평가영역과 겹치는 유효 셀)는 40.99%에 그쳤다** — "일부
구간에서 멈췄다"가 아니라 "끝까지는 갔지만 위치가 많이 틀렸다"는 실패
양상이다.

**핵심 결론**: 커스텀 코드(칼만필터, GICP, R보정, 디스큐, GPS 사후결합

사실상 0%**로 나온다. 즉 **이전 세션들이 도입한 커스텀 우회(GT pose
신뢰, 칼만필터 이상치방어, GPS 사후결합 등)는 "결과를 인위적으로 좋게
포장"한 게 아니라, GLIM 표준 파이프라인이 이 환경에서 스스로 해결하지
못하는 실제 정확도 문제를 메우기 위해 필요했던 것**이라는 근거가 이번
실험으로 확인됐다.
