# 14. 한계점 — unitree_guide 를 운용에 못 쓴 이유

> 작성 2026-08-20. 관련: docs/11, docs/13.
> 결론: **등판 성능은 unitree_guide 가 더 높지만(20도 vs 15도), 운용
> 컨트롤러는 RL robot_lab 으로 확정했다.** guide 는 Nav2 종단 주행에서
> 반복 전복했고 원인을 제거하지 못했다.

---

## 1. 무엇을 잃었는가

| 항목 | unitree_guide | RL robot_lab | 차이 |
|---|---|---|---|
| **등판 한계** | **20도** | 15도 | **-5도** |
| 등판 실패 양상 | 25도에서 **전복** (이탈 1.51~3.54 m) | 20도에서 **자세 유지 정지** (이탈 0.13~0.62 m) | RL 이 안전 |
| 단차 한계 | 150 mm (`gait_height 0.20` 일 때만) | 150 mm (기본값 그대로) | 동일 |
| 조정 손잡이 | `gait_height` 등 물리 파라미터 | 없음 (학습 정책 고정) | guide 가 유연 |
| **Nav2 종단 주행 (191 m)** | **전복, 실패** | **Goal succeeded, 오차 0.21 m** | **결정적** |

주행성 임계값도 함께 내렸다: `traversability_leg.yaml` 의
`max_slope_deg` **20.0 → 15.0**.

**다만 성동구 맵에서 이 하향의 실비용은 0으로 측정됐다.** 임계값을 내린
뒤 모듈 F 를 다시 돌렸더니 leg 주행 가능 셀이 **통과 24,614,986 / 불가
3,046,025 로 20도일 때와 완전히 동일**했다(파라미터가 실제 15.0 으로 적용된
것은 구동 중 `ros2 param get` 으로 확인). 도심 heightmap 이라 지면은 6도
이하이고 건물 벽은 거의 수직이라 **15~20도 대역에 해당하는 셀이 존재하지
않기 때문**이다.

즉 이 맵에서는 경로 선택지가 줄지 않는다. 다만 자연 지형이나 완만한
경사로가 있는 월드로 옮기면 그때는 실제 손실이 생긴다 — 그 경우 다시
재야 한다.

## 2. 증상

계단식 램프·단차 하네스에서 guide 는 정상 보행했다(등판 20도 3/3,
단차 150 mm 통과). 그런데 **같은 컨트롤러를 전체 파이프라인에 넣으면**
스폰(-195.7, 76.4) → 목표(-65.0, -62.4) 191 m 경로에서 전복했다.

```
roll  78도 -> 140도 -> -53도   (구르는 중)
[leg.controller_server] Resulting plan has 0 poses in it   x3
[leg.bt_navigator] Goal ABORTED
```

## 3. 배제한 원인

**(a) 지형이 아니다.** 정답 heightmap(`Seongdong_gu_aligned/mesh/height_map.png`)
으로 스폰→목표 직선 191 m 를 0.1 m 간격 400점 샘플링했다.

| 항목 | 값 |
|---|---|
| 경사 (기저 1 m) | 중앙값 2.1도, 90분위 4.5도, **최대 5.2도** |
| 단차 (0.1 m 셀) | 중앙값 0.005 m, **최대 0.012 m** |
| guide 한계 20도 초과 구간 | **0.0 %** |

경로 전체가 guide 등판 한계의 **1/4 이하**, 단차 한계의 **1/12 이하**다.

**(b) 파이프라인·지도·Nav2 설정이 아니다.** 컨트롤러만 RL 로 바꾸고
**나머지를 전부 그대로 둔 채** 다시 돌렸더니 목표에 도착했다.

```
[leg.bt_navigator] Goal succeeded
최종 (-64.93, -62.21)  목표 (-65.0, -62.4)  오차 0.21 m
자세 roll -0.15도, pitch -2.0도 | 계획 실패 0건 | "0 poses" 0건
```

**(c) 명령 끊김이 아니다.** `/leg/cmd_vel` 19.6 Hz(벽시계),
`/control_input` 19.0 Hz, RTF 0.456 → 시뮬 기준 약 42 Hz(설계 50 Hz).
컨트롤러는 200 Hz 로 도니 명령 하나당 약 5 주기가 확보된다. 중계기는
마지막 명령을 유지하므로 공백도 없다.

**(d) RTF 저하 자체가 아니다.** `use_sim_time` 환경에서 컨트롤러는
**시뮬 시간 기준** 200 Hz 를 그대로 받는다. RTF 가 낮으면 벽시계로 느려질
뿐이고, 오히려 시뮬 시간 기준 DDS 지연은 줄어든다. 부하가 문제가 되는
경로는 `controller_manager` 의 update 주기 초과(스킵)뿐인데, 이는 확인
전에 컨트롤러 교체로 결정이 나 **끝까지 측정하지 못했다.**

## 4. 시도한 대책과 결과

| # | 대책 | 근거 | 결과 |
|---|---|---|---|
| 1 | `gait_height` 0.08 → 0.20 | 발 들림이 80 mm 라 100 mm 턱에 걸림 | 단차는 해결, **전복은 그대로** |
| 2 | Nav2 한계를 guide 설계값에 맞춤 (`max_vel_x` 0.4, `max_vel_theta` 0.3, `acc_lim_x` 0.5, `acc_lim_theta` 0.6) | 병진·회전 동시 명령이 균형 여유를 잠식 | Nav2 지표는 깨끗해졌으나 **전복은 그대로** (roll 176 → 160 → 86도) |
| 3 | 명령 연속성 점검 | 명령 공백 가설 | **가설 기각** (3-c) |

## 5. 남은 가설 (미검증)

`StateTrotting` 의 명령 처리 구조가 Nav2 처럼 **선속도와 각속도가 동시에
계속 바뀌는** 입력을 전제하지 않은 것으로 보인다.

- `getUserCmd()` 는 요 명령에만 0.9 저역통과를 걸고 **선속도에는 필터가
  없다** (`StateTrotting.cpp:103`).
- `calcCmd()` 는 목표 속도를 현재 속도 ±0.2 로, `pcd_` 를 현재 위치
  ±0.05 로 포화시킨다. 명령이 빠르게 바뀌면 두 포화가 서로 상쇄되어
  균형 제어의 기준점이 흔들릴 수 있다.

램프 하네스는 명령이 일정했고(조향 ≤0.35 rad/s 직진), Nav2 는 그렇지
않다는 것이 두 조건의 유일하게 남은 차이다.

**후속 연구로 남긴다.** 선속도에 동일한 저역통과를 걸거나 `calcCmd()` 의
포화 폭을 명령 변화율에 맞춰 조정하면 guide 의 20도 등판을 되찾을 수
있을 가능성이 있으나, 이는 상위 컨트롤러 수정이므로 이번 범위를 벗어난다.

## 6. 되돌리는 법

```bash
ros2 launch agconav_bringup agconav_all.launch.py leg_controller:=guide
```

되돌린다면 `traversability_leg.yaml` 의 `max_slope_deg` 도 20.0 으로
함께 올려야 한다. 두 값은 짝이다.
